# Nitrogen — контекст и правила работы ИИ

## Назначение

Этот файл — стартовый контекст для новых чатов о разработке Nitrogen.

Перед предложением изменений ИИ обязан изучить актуальный код, сравнить его с Legacy и соблюдать приведённые ниже правила.

**Приоритет источников:**
1. Прямые указания разработчика.
2. Актуальные локальные файлы разработчика.
3. Актуальный код репозитория Nitrogen.
4. Исходный код Nitrogen.Legacy.
5. Настоящий документ.

При противоречиях необходимо сообщить разработчику, а не самостоятельно выбирать архитектурное решение.

## Проект

- Новый репозиторий: `Bodden007/Nitrogen`, ветка `main`.
- Источник переноса: `Bodden007/Nitrogen.Legacy`, ветка `master`.
- Назначение: кроссплатформенный HMI промышленной азотной установки.
- Технологии: C#, .NET 10, Avalonia 12, ReactiveUI.
- Целевые платформы: Desktop, Android, Browser; потенциально iOS.
- Источник телеметрии в перспективе — CoreLink.
- На текущем этапе используются демонстрационные данные.
- Общий UI не должен зависеть от Windows.
- Необходимо учитывать будущие trimming/AOT.

## Обязательные правила взаимодействия

### 1. Контроль изменений

**Никаких изменений без согласования с разработчиком.**

Порядок работы:

1. Изучить исходники.
2. Провести сравнение.
3. Выявить зависимости.
4. Предложить конкретное изменение.
5. Предупредить обо всех отличиях от Legacy.
6. Получить подтверждение.
7. Предоставить код.

Согласование одной операции не разрешает автоматически выполнять другие.

### 2. Перенос Legacy

Перенос выполняется с минимальными необходимыми изменениями.

Сохранять:

- XAML и визуальную структуру.
- Стили и ресурсы.
- Имена элементов.
- Binding и DataContext.
- Обработчики событий.
- Клавиатурное управление.
- Навигацию.
- Поведение экранов.
- Существующую функциональность.

**Запрещается самостоятельно удалять, упрощать или заменять функциональность.**

### 3. Законченный UI-модуль

Каждый экран переносится как законченный UI-модуль в пределах функциональности Legacy.

До написания кода необходимо проверить:

- Все Binding.
- DataContext и тип ViewModel.
- Свойства и типы данных.
- Реактивное обновление UI.
- Команды и обработчики.
- Клавиатурное управление.
- Навигацию.
- Состояние экрана при повторном открытии.
- Зависимости от других компонентов.

**Запрещается переносить только визуальную оболочку, оставляя известные зависимости для повторного прохода.**

### 4. ViewModel и демонстрационные данные

Использовать существующую архитектуру проекта.

На текущем этапе `MainViewModel` является общей моделью данных для главного экрана и подключённых экранов меню.

Новые ViewModel создавать только при технической необходимости и после согласования.

Правила:

- Существующие Binding из Legacy сохраняются.
- Необходимые свойства ViewModel создаются одновременно с переносом UI.
- Демонстрационные значения допускается жёстко задавать в ViewModel.
- Значения, жёстко заданные в Legacy XAML, необходимо явно помечать `TODO`.
- При согласованном переносе таких значений в ViewModel разметка переводится на Binding.
- Не подменять рабочие Binding статическими значениями.
- Не создавать дублирующие модели и свойства без необходимости.
- Не создавать новый экземпляр общей ViewModel при каждом открытии экрана.

`DataContext` может наследоваться через визуальное дерево Avalonia. Явное назначение допускается, если оно необходимо, но не должно добавляться автоматически без причины.

### 5. TODO и FIXME

`TODO` — запланированная работа или отсутствующая реализация.

`FIXME` — известный дефект, требующий исправления.

Для незавершённой функциональности Legacy:

- Сохранять обработчики и точки подключения.
- Ставить конкретный `TODO`.
- Указывать, какая именно функциональность отсутствует.
- Не придумывать алгоритм без технического задания.

**TODO не заменяет обязательный перенос существующей работоспособной функции.**

### 6. Архитектурные ограничения

Без согласования запрещено добавлять:

- Новые сервисы.
- Интерфейсы.
- DI-контейнеры.
- Фабрики.
- Механизмы навигации.
- Фоновые процессы.
- Дополнительные библиотеки.
- Рефакторинг существующей архитектуры.

Необходимо сохранять ранее утверждённые решения.

### 7. Работа с файлами

Перед изменением сравнивать исходный файл Legacy и актуальный файл Nitrogen.

Если локальные изменения ещё не опубликованы в GitHub, запрашивать актуальный файл у разработчика.

По умолчанию работать с одним файлом или одной согласованной небольшой правкой.

**Исключение:** разработчик может явно разрешить пакетное изменение нескольких связанных файлов, например подготовку всех моделей одного набора экранов.

Код предоставлять непосредственно в чате. Архивы и дополнительные файлы создавать только по запросу.

### 8. Проверка результата

Не утверждать, что код собран или работает, если проверка не проводилась.

Разделять:

- Успешную компиляцию.
- Успешный запуск.
- Проверку поведения UI.
- Проверку на конкретной платформе.
- Проверку промышленной функциональности.

При ошибках сначала анализировать конкретную причину, затем предлагать минимальное исправление.

### 9. Стиль взаимодействия

- Общение на русском языке.
- Технически, конкретно, без повторов.
- Не предлагать несогласованные улучшения.
- Не возвращаться к отклонённым решениям без новых оснований.
- Не скрывать изменения под видом переноса.
- Архитектурные решения принимает разработчик.

## Текущее состояние переноса (29.10.2026)

### Главный экран

- Главный экран Legacy перенесён в `Nitrogen/Views/MainView/MainView.axaml` как `UserControl`.
- `MainWindow` используется как Desktop-оболочка.
- `MainViewModel` содержит демонстрационные значения.
- CoreLink пока не подключён.

### Меню

- `MenuControl` перенесён из Legacy.
- Сохранена сетка 3×3 с девятью кнопками.
- Меню открывается через `ScreenHost`.
- Закрытие выполняется через `CloseRequested`.
- F8 открывает меню, Esc закрывает его.
- Закрытие приложения из меню реализовано разработчиком; перед изменениями необходимо изучить актуальный код.

### Навигация

Восстановлен принцип навигации Legacy через `ScreenNavigator`.

- `ShowScreen()` открывает экран и сохраняет предыдущий в стеке.
- `BackScreen()` восстанавливает предыдущий экран.
- `CloseScreen()` очищает историю и закрывает активный экран.
- Используются `IScreenNavigator` и `IScreenLoadable`.
- Обработка ошибок асинхронной загрузки остаётся техническим долгом.

Не заменять существующий механизм навигации без согласования.

### Клавиатура

Desktop `MainWindow` получает `KeyDown` и передаёт событие в `MainView.HandleKeyDown(e)`.

Активный экран обрабатывает команды через `IHotKeyScreen.HandleKey(Key)`.

Проверялась работа клавиатуры без предварительного клика мышью.

### TemperatureControl

Экран перенесён из Legacy.

Используются Binding к `MainViewModel`:

- `TemperatureOutlet` — демонстрационное значение `96`.
- `TemperatureVaporizer` — `85`.
- `TemperatureBath` — `75`.

Закрытие реализовано через `CloseRequested`.

### VolumeControl

Экран перенесён из Legacy.

Жёсткие значения XAML перенесены в свойства `MainViewModel`:

- `CementVolumeTotal` — `110`.
- `CementVolumeDs` — `60`.
- `CementVolumePs` — `50`.

Используются двусторонние Binding для редактируемых полей.

Обработчики установки и сброса объёма в Legacy не реализованы. Их необходимо сохранять с `TODO` до согласования алгоритма.

Закрытие реализовано через `CloseRequested`.

### Состояние общей ViewModel

Архитектурный принцип Legacy сохранён: общая реактивная модель обслуживает главный экран и связанные экраны.

Отличия:

- Legacy: `MainWindowViewModel`.
- Nitrogen: `MainViewModel`.
- Legacy: получение данных через Modbus Rx.
- Nitrogen: демонстрационные значения с перспективой подключения CoreLink.

Не считать текущую инфраструктуру получения данных полностью перенесённой из Legacy.
