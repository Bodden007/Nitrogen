# Правила архитектуры

- ARCH-001: обязательность и состав ядра определяются архитектурой проекта. Не заменять, не обходить и не дублировать утверждённое ядро без согласования.
- ARCH-002: ядро выполняет только утверждённые функции; границы ответственности фиксируются в документации проекта. Не переносить в него прикладную логику самовольно.
- ARCH-003: периферийные модули могут взаимодействовать напрямую через публичные API; не использовать ядро как посредник без необходимости. Отражать зависимости в графе.
- ARCH-004: абстракции только при доказанной необходимости. Прямая зависимость допустима. Не вводить интерфейсы, фабрики, адаптеры и слои ради гипотетического будущего.
- ARCH-005: новый модуль: назначение → границы ответственности → внутренний граф → публичный API → утверждение → реализация. Локальные изменения без изменения архитектуры не требуют повторного проектирования.
- ARCH-006/009: два уровня Mermaid-графов: глобальный `docs/ARCHITECTURE.md` и `MODULE.md` самостоятельного модуля. Глобальный граф содержит модули, пути, назначение, зависимости, точки интеграции и ссылки на паспорта. Внутренний — компоненты, API, зависимости, инварианты, Lifetime, ошибки, карту файлов и границы. Не отображать локальные переменные и приватные методы, кроме существенных для понимания алгоритмов. Обновлять документацию при изменении структуры/контрактов. Читать адресно; расширение контекста обосновывать. Не объединять исходники искусственно ради сокращения запросов.
- ARCH-007: локализовать изменения. Не менять потребителей при неизменном контракте; межмодульные изменения согласовывать. Посторонние проблемы сообщать отдельно.
- ARCH-008: циклические архитектурные зависимости запрещены; двусторонний обмен данными допустим. Направление зависимостей явно обозначать. Ядро не зависит от прикладных потребителей.
- ARCH-010: SOLID: одна ответственность и причина изменения; расширение без изменения стабильного кода, где оправдано; соблюдение поведенческих контрактов; отсутствие зависимости от ненужных API; высокоуровневые компоненты не привязывать к заменяемым низкоуровневым деталям без основания. Применять совместно с ARCH-004.
- ARCH-011: взаимодействие только через утверждённый публичный контракт. Не менять методы, свойства, события, DTO, статусы, сигнатуры и семантику без разрешения. Для изменения представить проблему, доказательства недостаточности API, предложение, альтернативу без изменения, затронутых потребителей и риски. Исключения не пересекают публичные границы; ожидаемые ошибки обрабатываются внутри, наружу — утверждённые результаты/статусы; не подавлять ошибки молча, диагностические механизмы согласовывать.
- ARCH-012: предупреждать о дублировании, обнаруженном в уже прочитанном контексте, обязательно отмечать при Code Review. Не искать по всему репозиторию без задачи. Не объединять реализации и не выделять общие компоненты без решения разработчика.
- ARCH-013: владение состоянием, памятью и ресурсами, создание/уничтожение, Lifetime, ссылки, указатели, передача владения, Dispose, singleton/scoped/transient, Rx-подписки, кеширование определяет разработчик. Сохранять утверждённые механизмы; альтернативы обосновывать.
- ARCH-014: согласовывать потоки, Task.Run, async/sync, блокировки, параллелизм, Rx Scheduler, UI dispatch, таймеры и фоновые задачи. Предупреждать о гонках, дедлоках и нарушении последовательности; не менять модель исполнения самовольно.
- ARCH-015: приоритет стандартной библиотеки языка/платформы, затем согласованные зависимости, собственная реализация на STD, новая зависимость только по разрешению. Не добавлять, удалять, заменять или обновлять зависимости самостоятельно. Обосновывать необходимость, альтернативы, лицензию, сопровождение, платформы, архитектуры, AOT/trimming (если применимо), нативные и транзитивные зависимости, стоимость замены. Не писать сложные протоколы или криптографию самостоятельно только ради STD — согласовать решение.
- ARCH-016: обратная совместимость не вводится автоматически. Не сохранять старые API, адаптеры, перегрузки, Obsolete и форматы ради гипотетических потребителей. Согласовать последствия для реальных потребителей и прекращение поддержки.
- ARCH-017: перед интеграцией проверить API, направления зависимостей и данных, инициатора, владение, порядок запуска/остановки, ошибки, типы, единицы, форматы, аллокации, копирование и модель исполнения. Несовместимость вынести на согласование, не создавать адаптер самовольно. Обновить графы.
